# Extraction service deploy image dependencies (T1b, goal mist-two-loop / MIS-171).

# This is the measured third-party import closure of
# `python -m backend.extraction_service` (T1a's brief), not
# `backend/requirements.txt` -- that file targets the full voice+graph
# backend image and leaves most of this list unpinned (it relies on the
# torch/chatterbox install order in docker/backend/Dockerfile to pull them
# in transitively). Every module below IS actually imported at process
# start; verified 2026-09-26 by running the service's entry import
# (`import backend.extraction_service.app`) inside the worker container and
# reading `sys.modules`.
#
# Pin policy: where backend/requirements.txt or the repo root
# requirements.txt already pins a distribution with `==`, that pin is used
# here unchanged. Everything else is pinned to the version installed in
# this worker's container (`pip show <name>` / `pip list --format=freeze`,
# read 2026-09-26) -- backend/requirements.txt itself leaves these
# unpinned (`>=`), so there is no in-repo exact pin to copy.
#
# Module (as imported) -> distribution (as installed) -> why it's here:
#   annotated_types   -> annotated-types    pydantic dependency
#   anyio             -> anyio              httpx/starlette async backend
#   brotli            -> brotli             httpx optional content-encoding
#   click             -> click              uvicorn dependency

#   distro            -> distro             openai client OS fingerprint for its User-Agent
#   dotenv            -> python-dotenv      backend.knowledge.config calls load_dotenv()
#   fastapi           -> fastapi            backend.extraction_service.app
#   httpx             -> httpx              LlamaHealthProbe + openai client transport
#   idna              -> idna               httpx dependency
#   neo4j             -> neo4j              see NEO4J/PANDAS/PYARROW note -- never queried
#   numpy             -> numpy              backend.knowledge.extraction.pipeline
#   openai            -> openai             backend.llm.llama_server_provider.LlamaServerProvider

#   pandas            -> pandas             see NEO4J/PANDAS/PYARROW note -- never used

#
# uvicorn is added per the T1b brief (not in the measured import-closure
# list because that list names modules `app.py`/`engine.py` import, and
# uvicorn is imported one level up, by `backend/extraction_service/__main__.py`).
#
# NEO4J/PANDAS/PYARROW: none of the three is called by any code path this
# service executes -- there is no graph query and no DataFrame anywhere in
# backend/extraction_service/. All three load anyway, as a chain of package
# __init__ side effects, traced 2026-09-26 by hooking builtins.__import__
# and importing backend.extraction_service.app:
#   1. backend.knowledge.extraction's package __init__ eagerly imports
#      pipeline.py (backend/knowledge/extraction/pipeline.py), which imports
#      GraphStore -- and importing ANY submodule of backend.knowledge.extraction
#      (engine.py imports several) runs that __init__ first. This executes
#      even though engine.py/app.py never import pipeline.py or GraphStore
#      by name.
#   2. GraphStore lives under backend.knowledge.storage. Importing ANY of
#      its submodules (graph_store, graph_executor -- normalizer.py and
#      internal_derivation.py both import graph_executor) runs
#      backend/knowledge/storage/__init__.py first, which unconditionally
#      imports Neo4jConnection from neo4j_connection.py.
#   3. neo4j_connection.py does `from neo4j import Driver, GraphDatabase` --
#      this is the actual `import neo4j`.
#   4. The neo4j driver's own `neo4j/_optional_deps/__init__.py` runs
#      `try: import pandas as pd except ImportError: pass` at module level
#      (an optional helper for `Result.to_df()`, which this service never
#      calls). pandas IS installed (it is a dependency of this repo's main
#      backend, per requirements.txt's lancedb/sentence-transformers), so
#      the try succeeds and pandas loads unconditionally.
#   5. pandas' own `pandas/compat/pyarrow.py` submodule does an
#      unconditional `import pyarrow` as part of pandas's own init chain
#      (a version-compat probe, not guarded the way neo4j's pandas probe is).
# Net effect: omitting these three would raise no ImportError today (step 4's
# probe is guarded), but it changes the measured closure this file exists to
# reproduce, and neo4j/pandas/pyarrow's own absence is untested here. They
# stay pinned.
